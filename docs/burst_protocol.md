# MCU → FPGA burst transfers

Status: draft v1. The firmware side is implemented. Cores that do not implement it keep working unchanged.

## Why

The classic link sends one 3-byte frame (`cmd, addr, data`) per data byte, with MCU_SS toggled around every frame. ROMs, file loader data and ioctl data also need extra bank frames (`CMD_ROMBANK`, `CMD_FILEBANK`, `CMD_IOCTL_BANK`) every 256 bytes. About 2/3 of the bus time is overhead.

A burst sends one short header and then up to 512 data bytes back to back, under a **second chip select**. The classic protocol and MCU_SS stay exactly as they are, so old cores, which never see the second chip select, are not affected.

## Signals

| Signal | Direction | Meaning |
|---|---|---|
| `BURST_CS_N` | MCU → FPGA | Burst chip select, active low. Shares SCK / MOSI / MISO with the classic link. |
| `BURST_READY` | FPGA → MCU | 1 = the FPGA can accept a full burst (512 bytes) now. Optional, see capabilities. The MCU input has a pull-down, so an undriven line reads as 0. |

Pin mapping. The RP2040 side uses the firmware names `PIN_MCU_SPI_IO0/1` from `src/config.h`. **On Go, the FPGA port index is swapped.**

| Board | Signal | RP2040 GPIO (firmware) | FPGA port in the core top | FPGA pin |
|---|---|---|---|---|
| Go | `BURST_CS_N` | GPIO14 (`PIN_MCU_SPI_IO0`) | `MCU_SPI_IO[1]` | M11 |
| Go | `BURST_READY` | GPIO2 (`PIN_MCU_SPI_IO1`) | `MCU_SPI_IO[0]` | N9 |
| Mini | `BURST_CS_N` | GPIO14 (`PIN_MCU_SPI_IO0`) | `MCU_IO[0]` | G6 |
| Mini | `BURST_READY` | GPIO15 (`PIN_MCU_SPI_IO1`) | `MCU_IO[1]` | F6 |
| Mini G | `BURST_CS_N` | GPIO14 (`PIN_MCU_SPI_IO0`) | `MCU_IO[0]` | G6 |
| Mini G | `BURST_READY` | GPIO15 (`PIN_MCU_SPI_IO1`) | `MCU_IO[1]` | F6 |

**MCU_IO4 is not available.** On Mini boards before Rev.G with the [FT812 clock mod](https://github.com/andykarpov/karabas-mini/blob/master/revF_mod.md), it carries the 8 MHz FT812 clock generated by the FPGA. On Rev.G it is no longer connected to the RP2040. The firmware keeps GPIO18 an input.

The MCU drives `BURST_CS_N` only after the loaded core has announced burst support (see below). Until then the pin is an input, as before. It returns to input at every core load.

## Capability query (`CMD_CAPS = 0xF7`)

During every core load the MCU asks the core what it supports, using the classic link. The query comes after `CMD_INIT_START` and `CMD_HW_SETUP`, before ROMs are sent.

1. MCU sends the classic frame `{0xF7, 0x00, 0x01}`. `addr = 0x00` means "query", `data = 0x01` is the protocol version.
2. MCU then sends up to 16 `CMD_NOP` frames. A core that supports bursts answers in the **reply bytes** of any of these transfers (the bytes the FPGA shifts out on MISO), with the frame `{0xF7, caps, max_mhz}`. Cores that send to the MCU through a queue can answer through it: frames already queued ahead of the answer (e.g. the NOPs some cores keep queued) only delay it, and should stay well below 16.
   - `caps` bit 0: burst write supported.
   - `caps` bit 1: `BURST_READY` is driven by the core. If 0, the MCU does not look at it.
   - `caps` bit 2: burst read supported (see "Burst read" below; requires bit 1).
   - `caps` bits 7..3: reserved, 0.
   - `max_mhz`: the highest SCK frequency during bursts, in MHz. 0 means the normal link clock (16 MHz, or the core's `spi_freq`). Boards before Mini Rev.G do not have MCU_SCK on a global clock pin, so a core there that samples SCK with its system clock must report a frequency it can oversample safely.
3. No answer means classic transfers only. Old cores ignore the unknown command 0xF7.

## Burst write transaction

```
BURST_READY must be 1 (only if caps bit 1)
BURST_CS_N  ‾‾\_________________________________________________/‾‾
MOSI           TYPE  A31..24  A23..16  A15..8  A7..0  D0  D1 ... Dn-1
```

- SPI mode 0, MSB first, 8-bit bytes, up to `max_mhz`.
- Header: 5 bytes, `TYPE` followed by the 32-bit big-endian start address `ADDR`.
- Payload: 1 to 512 bytes. Byte `k` is written to `ADDR + k`. The burst ends when `BURST_CS_N` goes high.
- MCU_SS (classic) and `BURST_CS_N` are never low at the same time.
- During a burst write the FPGA must not drive MISO (keep the classic behaviour: drive it only while MCU_SS is low). The MCU ignores MISO during bursts.
- The MCU checks `BURST_READY` only between bursts, never inside one. The core must keep it at 1 only while it can take a whole 512-byte burst at `max_mhz`.
- If `BURST_READY` stays 0 for 100 ms, the MCU falls back to classic frames for the rest of that transfer.

`TYPE` selects the target. It uses the code of the classic data command it replaces, so the core can feed the same internal write strobe:

| TYPE | Replaces (classic) | Target in the core |
|---|---|---|
| `0x07` (`CMD_ROMDATA`) | `CMD_ROMBANK` + `CMD_ROMDATA` | ROM loader: `ROMLOAD_ADDR` / `ROMLOAD_DATA` / `ROMLOAD_WR` |
| `0x0D` (`CMD_FILEDATA`) | `CMD_FILEBANK` + `CMD_FILEDATA` | File loader data |
| `0x53` (`CMD_IOCTL_DATA`) | `CMD_IOCTL_BANK` + `CMD_IOCTL_DATA` | Ioctl (OSD file loader) data |

`TYPE` bit 7 = 1 marks a read request (see "Burst read" below). A core must ignore a burst with an unknown `TYPE`, discarding bytes until `BURST_CS_N` goes high.

Everything around the data stays classic and unchanged: `CMD_ROMLOADER` start/stop, `CMD_FILELOADER` reset/active, and `CMD_IOCTL_STATE` / `SLOT` / `SIZE` / `EXT`. Bursts replace only the bank + data frames between them.

## Burst read (FPGA → MCU), planned

Status: specified, not implemented yet on either side. It is meant for data the FPGA produces, e.g. disk sectors written by the core for the file mounter. Requires caps bits 1 and 2.

The FPGA usually needs time to fetch the data (from SDRAM, a sector buffer, ...), so a read takes two chip-select phases with `BURST_READY` as the handshake:

```
1. request:  BURST_CS_N low:  TYPE|0x80, A31..24, A23..16, A15..8, A7..0, LEN15..8, LEN7..0   BURST_CS_N high
             FPGA: BURST_READY -> 0, starts fetching LEN bytes from ADDR into its output buffer
2. wait:     MCU waits for BURST_READY = 1 (data is ready), with the same 100 ms timeout
3. data:     BURST_CS_N low:  MCU clocks out 1 + LEN bytes (MOSI = 0x00)
             MISO: 1 turnaround byte (ignored by the MCU), then D0 .. DLEN-1
             BURST_CS_N high
```

- `LEN` is 1..512, big-endian.
- The turnaround byte gives the FPGA one byte time after `BURST_CS_N` falls to put D0 into its MISO shift register, so it does not need D0's first bit before the first SCK edge.
- During the data phase, and only then, the FPGA drives MISO from the burst logic: `MCU_MISO <= spi_miso when MCU_SS = '0' else burst_miso when BURST_CS_N = '0' and read pending else ...`. During the request phase and during write bursts it does not drive MISO.
- After the data phase the read is finished. Any other burst, or a new request, starts from the header again. If the MCU times out waiting for `BURST_READY`, it raises `BURST_CS_N` without a data phase; the core drops the pending read at the next request header.
- MCU side (planned): `link_burst_read(type, addr, buf, len)`, used only when caps bit 2 is set.

## Firmware side

- `link_caps_query()` runs in `do_configure()`. `link_burst_available()` / `link_burst_write()` are in `src/fpga/link.cpp`.
- The users are `rom_send()` (ROMs), the file loader and the ioctl loader. They fall back to classic frames from the first byte a burst could not send.
- The `debug=1` log prints the answer: `FPGA caps: ...` or `FPGA caps: none (classic link)`.
