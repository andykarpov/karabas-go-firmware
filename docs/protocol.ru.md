# Протокол обмена MCU ↔ FPGA

[English version](protocol.md) · Burst-передачи: [burst_protocol.md](burst_protocol.md) · Файлы ядер и `core.json`: [karabas-go-tools/make_core](https://github.com/andykarpov/karabas-go-tools/tree/master/make_core)

RP2040 (MCU) и ядро в FPGA общаются по одному SPI-линку. По нему MCU:

- передаёт события ввода, отрисовку OSD, ROM и файлы, регистры RTC и настройки;
- получает то, что нужно ядру от него: записи в RTC, байты UART, рисование на LED-матрице, отладочные значения.

Здесь описан линк так, как его реализует прошивка (`src/fpga/link.cpp`, коды `CMD_*` в `src/config.h`). На стороне FPGA в каждом ядре своя копия `mcu.vhd`. Эталонная реализация — TS-Conf (`karabas-go-core-tsconf/src/rtl/mcu/mcu.vhd`).

## 1. Физический уровень

| Сигнал | Направление | Примечание |
|---|---|---|
| `MCU_SCK` | MCU → FPGA | Такт SPI. По умолчанию 16 МГц; ядро может задать другую частоту полем `spi_freq` в своём `core.json`. |
| `MCU_MOSI` | MCU → FPGA | |
| `MCU_MISO` | FPGA → MCU | FPGA управляет линией только пока `MCU_SS` в нуле. |
| `MCU_SS` (`MCU_CS_N`) | MCU → FPGA | Выбор кадра, активный ноль. |
| `MCU_IO` / `MCU_SPI_IO` | в обе стороны | Дополнительные линии, разные на разных платах. По ним идут выборки FT812 и SD2 (их коммутирует FPGA, см. `CMD_SPI_CONTROL`), а также chip select и READY для burst ([burst_protocol.md](burst_protocol.md)). |

SPI mode 0, старшим битом вперёд, байты по 8 бит.

По этой же шине SPI0 доступен видеочип FT812. Когда ядро его включает (`CMD_SPI_CONTROL`), FPGA переключает шину на FT812 с его собственной выборкой.

## 2. Кадры

Каждая передача — это **кадр** из 3 байт, на время которого `MCU_SS` опущен:

```
MCU_SS   ‾‾\______________________/‾‾
MOSI        CMD     ADDR    DATA          MCU → FPGA
MISO        CMD'    ADDR'   DATA'         FPGA → MCU, в той же передаче
```

- `CMD` задаёт команду, `ADDR` и `DATA` — два её аргумента.
- В той же передаче FPGA выдвигает свой кадр `CMD' ADDR' DATA'` для MCU — обычно следующую запись из своей выходной очереди. Если сказать нечего, FPGA шлёт `FF 00 00` (`CMD_NOP`).
- FPGA может говорить только тогда, когда передачу начал MCU. Поэтому прошивка отправляет кадр `CMD_NOP`, если за проход основного цикла линк простаивал (`link_poll()`).
- Каждый ответный кадр, для `CMD` которого есть обработчик, передаётся этому обработчику (`link_on()` в прошивке). Пока ядро конфигурируется, ответы игнорируются.

**Многобайтные значения** передаются несколькими кадрами с одним `CMD`: `ADDR` — номер байта с 0, младший байт первым (`spi_send16/24/32/64`). Пример: `CMD_IOCTL_SIZE` = 1000 (0x3E8):

```
51 00 E8   51 01 03   51 02 00   ...   51 07 00
```

**Пары «банк + данные».** Данные ROM, file loader и ioctl передаются так: кадры банка несут биты адреса 31..8, кадры данных — биты 7..0:

```
BANK  addr=0 data=A15..8 / addr=1 data=A23..16 / addr=2 data=A31..24   (когда они меняются)
DATA  addr=A7..0 data=байт
```

Burst заменяет эти пары гораздо более быстрой передачей, см. раздел 7.

### Сторона FPGA

Ядра используют `spi_slave.vhd` со словом 24 бита (`N => 24`):

- `do_valid` — строб «кадр принят». Он может длиться 2 такта, поэтому берите его по переднему фронту.
- `di_req` — запрос следующего исходящего слова. Ядра держат небольшую FIFO (`queue`) исходящих кадров и забирают из неё по `di_req`; в некоторых ядрах в очереди всегда лежит несколько NOP.

Неизвестные ядру команды должны игнорироваться.

## 3. Последовательность при запуске ядра

`do_configure()` в `src/fpga/core_loader.cpp`, при каждой загрузке ядра:

1. Битстрим заливается через пины конфигурации FPGA (не через этот линк).
2. `CMD_INIT_START` — ядро показывает, что занято.
3. `CMD_HW_SETUP` `(0, HW_ID)` и `(1, dvi_only)`.
4. Запрос `CMD_CAPS`, на который отвечают только ядра с поддержкой burst или backup RAM. См. раздел 7.
5. Шрифт OSD: `CMD_OSD` — сброс шрифта и данные шрифта.
6. ROM: `CMD_ROMLOADER` вкл., данные ROM, `CMD_ROMLOADER` выкл.
7. Значения переключателей OSD (`CMD_SWITCHES`) и регистры RTC (`CMD_RTC`).
8. Сброс клавиатуры: `CMD_USB_KBD` 0..6 = 0.
9. `CMD_INIT_DONE` — ядро может стартовать.

| `52` | `CMD_IOCTL_BANK` | номер байта 0..2 | биты адреса файла 15..8 / 23..16 / 31..24 | |
| `53` | `CMD_IOCTL_DATA` | биты адреса 7..0 | байт файла | |
| `54` | `CMD_IOCTL_EXT` | номер символа | символ расширения | В нижнем регистре, без точки. |
| `55` | `CMD_IOCTL_STATE` | 0 | 1 = начало, 0 = конец | |
| `63` | `CMD_MATRIX_BTN` | кнопка 0..3 | 1 / 0 | Кнопки платы LED-матрицы ([matrix.md](matrix.md)). |

| `F9` | `CMD_HW_SETUP` | 0 = плата, 1 = только DVI | 0: `HW_ID` (1 Go, 2 Mini, 3 Mini G); 1: 0 / 1 | |
| `FA` | `CMD_RTC` | регистр | значение | Регистр RTC; набор регистров зависит от `rtc_mode` (MC146818A, DS1307, ZX Evolution, MSM6242B). |

| `FE` | `CMD_INIT_DONE` | 0 | 0 | Конфигурация закончена (BUSY = 0). |

## 6. Последовательности

### ROM (`roms` в core.json)

```
08 00 01                        загрузчик ROM вкл.
06 00 a15..8  06 01 a23..16  06 02 a31..24      только когда меняются биты 31..8
07 a7..0 байт                   по кадру на байт
...
08 00 00                        загрузчик ROM выкл.
```

Ядро пишет каждый байт по адресу `address + смещение`. Запись ядра определяют по смене адреса или по стробу `CMD_ROMDATA`.

### File loader (ядра `fileloader`)

```
0E 00 03   0E 00 02             сброс + активен, затем активен
0C ... / 0D ...                 банк + данные, как у ROM, смещение в файле с 0
0E 00 00                        готово
```

### Ioctl-загрузчик (пункты OSD `FL`)

```
55 00 01                        начало
50 00 слот
51 i size_i  (i = 0..7)         сначала размер 0, затем реальный
54 i char_i                     расширение, например "rk"
52 i bank_i  (i = 0..2) / 53 a7..0 байт     банк + данные
55 00 00                        конец
```

Файл отправляется, когда его выбирают в OSD. Пункт `FL` с `autoload` (бит 7 байта слота) и существующим файлом (`dir` / `filename` из `core.json` или выбранный последним) отправляется и при запуске ядра, после переключателей и до `CMD_INIT_DONE`, например Kickstart ядра NanoMig.

### File mounter (пункты OSD `F`)

Файл образа слота остаётся открытым (на чтение и запись, если можно), пока работает ядро. Сектор — 512 байт, нумерация от начала файла.

Монтирование: при запуске ядра для каждого пункта `F` с сохранённым файлом и при выборе файла в OSD.

Извлечение: Del / Backspace на пункте `F` в OSD или `[ Eject ]` в начале его файлового браузера. Прошивка посылает только кадры с размером 0 и забывает файл в настройках ядра. Переход по каталогам в браузере не меняет смонтированный образ.

```
40 00 slot
41 i 00      (i = 0..7)         размер 0: извлечение
41 i size_i  (i = 0..7)         образ; без файла не отправляется
```

Физический дисковод (Karabas Go: `board_has_floppy()`, и пункт `F` с флагом `physical` в `core.json`, бит 0 байта после типа пункта). В его файловом браузере после `[ Eject ]` есть пункты `[ Physical DF0 ]` / `[ Physical DF1 ]` (дисковод DS0 / DS1 разъёма дисковода). Дисковод бывает только в одном слоте: выбор извлекает его из другого слота. В настройках ядра файлом слота хранится имя `:phys0` / `:phys1`. Каждое монтирование — смена дискеты для ядра; следующие кадры размера слота (извлечение, образ) его отменяют.

```
40 00 slot
41 i 00      (i = 0..7)         размер 0
46 slot drive                   1 = DS0, 2 = DS1
```

Запрос чтения (ядро отправляет свои кадры в ответных байтах):

```
FPGA: 42 i lba_i (i = 0..3), 43 slot 01
MCU:  данные сектора: обычные кадры 44 00 offset_hi / 45 offset_lo byte
      (или burst типа 45, адрес = смещение 0..511)
MCU:  42 00 sum_lo, 42 01 sum_hi
MCU:  43 slot 01 (готово) или 43 slot 02 (ошибка: нет файла, сектор за его концом или неполный запрос)
```

Запрос записи:

```
FPGA: 42 i lba_i (i = 0..3), 43 slot 02,
      затем 512 байт: 44 00 offset_hi / 45 offset_lo byte, затем 44 10 sum_lo, 44 11 sum_hi
MCU:  опрашивает NOP-кадрами, пока не придут 512 байт и сумма, и пишет сектор
MCU:  43 slot 01 (готово) или 43 slot 02 (ошибка: данные потеряны, нет файла)
```

Один запрос за раз: ядро ждёт `43 slot status` перед следующим.

Раньше на линии изредка терялись кадры (на Mini G: всплески на chip select и очередь ответов, которая брала два слова за один кадр; оба исправлены в ядре). Запросы по-прежнему проверяются от начала до конца:

- прошивка принимает запрос, только если после `42 00` пришли все четыре байта `42`, иначе отвечает `43 slot 02`;
- ядро принимает чтение, только если пришли 512 байт и сумма совпала; прошивка пишет сектор, только если пришли все 512 байт и сумма совпала;
- ядро повторяет запрос после ответа с ошибкой или если ответа нет 200 мс (потерян `43`).

Данные сектора при чтении прошивка отправляет одним burst-ом, если ядро объявило поддержку burst, иначе обычными кадрами (ими же досылается то, что burst не отправил). Ядро в обоих случаях проверяет сумму и передаёт сектор дальше, только если он полный и верный. Данные запроса записи вместе с самим запросом не помещаются в очередь ответов `mcu.vhd` (512 записей), поэтому ядро кладёт их в очередь, пока в ней есть место. Неполный последний сектор при чтении дополняется нулями.

### Backup RAM (`.sav`, ядра с битом 3 в caps)

Память картриджа на батарейке (NES и подобные) хранится в файле рядом с играми. Размер решает ядро (только оно знает правила маппера) и просит файл после загрузки игры; прошивка игру не разбирает. Файл — сырой дамп backup RAM, как у MiSTer и эмуляторов.

```
FPGA: 48 00 size_0, 48 01 size_1, 48 02 size_2, 48 03 size_3   размер в секторах по 512 байт (LE)
FPGA: 48 10 slot                                                img-слот для файла
FPGA: 48 80 kind                                                0 = .sav (n = снапшот n, позже)
MCU:  открывает или создаёт <каталог сейвов>/<имя игры без расширения>.sav не меньше size секторов
      (новые байты 0) и подключает его в слот как file mounter: 40 00 slot, 41 i 00,
      41 i file_size_i. Без файла (нет имени игры, нет SD-карты, только чтение): только кадры размера 0.
```

Каталог сейвов — поле `save_dir` заголовка ядра (`FILE_POS_SAVE_DIR`, 32 байта), а если оно пустое — `<каталог fileloader>/saves`. Ядро читает секторы обычными запросами чтения до старта своего CPU и пишет изменённые CPU секторы обычными запросами записи через секунду после последней записи (или через несколько секунд после первой — для игр, которые пишут всё время). Ядро, не получившее подключения примерно за секунду, работает без сейва (прошивка без этой команды).

Flush — перед загрузкой другой игры, другого ядра, перезагрузкой (хоткей, `AT+KARABAS=boot`) и входом в USB mass storage:

```
MCU:  47 slot 00
FPGA: запросы записи грязных секторов (прошивка обслуживает их, пока ждёт)
FPGA: 47 slot 01 (грязных секторов нет) или 47 slot 02 (запись не удалась)
MCU:  ждёт ответа до 3 с, затем sync и закрывает файл (кадры размера 0 ядру)
```

### Оверлей OSD (`CMD_OSD`)

| ADDR | Регистр |
|---|---|
| `01` | Показать: 1 / 0 |
| `02` | Popup: бит 0 = показать, биты 7..4 = номер popup (его смысл определяет оверлей ядра), 0 = скрыть |
| `0F` | Очистить |
| `10` / `11` | Курсор X / Y |
| `12` / `13` | Символ / атрибут в позиции курсора |
| `14` | Нет операции |
| `20` | Сброс шрифта |
| `21` / `22` | Байт шрифта / строб записи байта шрифта |

Прошивка хранит копию экрана и отправляет только изменившиеся знакоместа.

### RTC

При запуске ядра прошивка отправляет все регистры RTC, затем каждые 500 мс — регистры времени. В обоих случаях это `CMD_RTC (регистр, значение)`. Когда процессор ядра пишет в регистр, ядро присылает `CMD_RTC` обратно, и прошивка записывает его в микросхему RTC. Форматы:

- **MC146818A:** BCD или двоичный, выбирается регистром B.
- **DS1307:** BCD.
- **ZX Evolution:** регистры MC146818A, всегда BCD.
- **MSM6242B** (`rtc_mode` 3, часы Amiga по адресу $DC0000): регистры 0-12, по одной BCD-цифре: S1 S10 MI1 MI10 H1 H10 D1 D10 MO1 MO10 Y1 Y10 W (год по модулю 100, W = 0 — воскресенье), 24 ч. Управляющие регистры D, E, F — в ядре. Ядро присылает цифры, которые пишет процессор; прошивка устанавливает микросхему часов через 100 мс после последней из них (процессор пишет время по одной цифре) и до этого не отправляет время.


### USB-принтер: данные и состояние

| Направление | Кадр (hex) | Значение |
|---|---|---|
| FPGA → MCU | `13 00 xx` | Один байт принтеру без преобразования |
| FPGA → MCU | `14 00 00` | Необязательный запрос состояния; включает обновления |
| MCU → FPGA | `14 00 ss` | Только состояние принтера |

`ss` равен `80` (бит 7 BUSY установлен) или `00`; биты 6..0 нулевые.
Подтверждений отдельных байтов и команд сброса по SPI нет. Ненулевые адреса
игнорируются. BUSY означает отключение, неизвестный статус или неготовность
принтера, ошибку/сброс сервиса, малый остаток места (32 байта или меньше) либо
отложенный байт DATA. Размер очереди остаётся 2048 байт; запас нужен для SPI-байтов
в пути. При освобождении места и готовности принтера BUSY снимается автоматически.
После запуска FPGA устанавливает BUSY=1.

DATA сразу ставится в очередь обработчиком APP. Последовательные байты не требуют
подтверждения. MCU передаёт изменения состояния из APP-цикла и отвечает на запросы.
Кадр состояния никогда не подтверждает приём байта. Обновления включаются первым
запросом состояния или DATA; старым ядрам сообщения принтера не отправляются.
До первого успешного чтения USB-статуса держится BUSY=1, в том числе при подключении
без бумаги. USB-статус опрашивается раз в секунду.

При ограничении записей Z80 FPGA должна учитывать задержку SPI FIFO и обновления
статуса: сохранённый BUSY=0 не резервирует место. Один байт, пришедший в полную
очередь, удерживается в отдельном регистре протокола и передаётся при освобождении
места раньше следующих байтов. Дальнейшее переполнение учитывается счётчиком
отклонённых байтов, но не фиксирует BUSY навсегда. При смене сеанса отложенный байт
отбрасывается. Запас в 32 байта не гарантирует защиту при произвольной глубине FIFO
FPGA. Протокол не гарантирует доставку при переполнении или потере SPI-кадров.

Загрузка ядра очищает состояние протокола и запрашивает сброс сервиса, если остались
данные или ошибка сервиса. Явное восстановление доступно через локальный API
`printer_reset()`, а не SPI-команду. Проверка сеанса при записи защищает от гонки
с отключением/сбросом. Уже переданные принтеру байты отозвать нельзя.

### Диагностика принтера (`15`)

Временное диагностическое расширение: удалено из FPGA GO после успешной
повторной проверки печати с исправленным SPI. Текущее ядро игнорирует `15`;
счётчики и CRC принтера удалены. Ниже сохранён формат прежних диагностических
сборок. Поддержка этих сборок в RP2040 остаётся.

MCU запрашивает снимок командой `15 00 tag`. Ядро GO отвечает `15 80 tag`,
затем 28 кадрами `15 index byte` (индексы `00..1B`) и завершает `15 81 tag`.
Первые 24 байта — шесть uint32 little-endian: число OUT Z80, CRC данных Z80,
число отклонённых OUT, число принятых FIFO кадров DATA, число завершённых
SPI-кадров DATA, CRC данных этих SPI-кадров. Последние четыре байта — CRC
первых 24 байтов. Все CRC: CRC-32/ISO-HDLC, начальное значение и финальный XOR
FFFFFFFF, отражённый полином EDB88320.

Снимок фиксируется при запросе; ответ имеет низший приоритет в очереди.
Запрос во время постановки предыдущего ответа в очередь игнорируется.
Неполный, повреждённый или переставленный ответ отбрасывается. Следующий
диагностический запрос использует новый tag; DATA при этом не повторяется.
Команды `13` и `14` не изменены. При `debug=1` RP2040 запрашивает снимок
после 500 мс без данных принтера, не чаще раза в две секунды.
Сравнивать значения нужно после завершения печати, при `settled=1`.
Перед тестом следует перезагрузить ядро, чтобы сбросить счётчики обеих сторон.

## 7. Возможности ядра и burst-передачи

`CMD_CAPS` (`F7 00 01`) спрашивает ядро, что оно умеет. Затем прошивка опрашивает его до 16 кадрами NOP. Ядро с поддержкой burst или backup RAM отвечает `F7 caps max_mhz` в ответном кадре:

- бит 0 caps: burst-запись;
- бит 1: ядро управляет `BURST_READY`;
- бит 2: burst-чтение (запланировано);
- бит 3: backup RAM (`CMD_BK_MOUNT`, `CMD_IMG_FLUSH`, раздел 6): прошивка делает flush сейва ядра перед загрузкой другой игры или ядра.

Старые ядра не отвечают и остаются на обычных кадрах.

Burst идёт по второму chip select. За 5-байтным заголовком (тип + 32-битный адрес) следует до 512 байт данных. Он заменяет пары «банк + данные» у ROM (`07`), file loader (`0D`) и ioctl (`53`). Полная спецификация — в [burst_protocol.md](burst_protocol.md).

При `debug=1` в логе видны ответ caps и время передач.
