# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

This is the RP2040 (Raspberry Pi Pico) MCU firmware for the Karabas Go family of FPGA retro-computer boards. It is C11 on the pico-sdk 2.2.0 with FreeRTOS SMP (V11.2.0) and TinyUSB 0.18, built with CMake. The MCU acts as the FPGA's companion. It loads bitstreams from the SD card, runs the OSD menus, handles USB/PS2/Sega input and the RTC, exposes the SD card as USB mass storage, and talks to the running FPGA core over SPI.

## Build / upload

Each board is a CMake target, which sets `HW_ID`:

| Target | HW_ID | Board | Core file ext | Release file |
|---|---|---|---|---|
| `karabas_go` | 1 | Karabas Go | `.kg1` | `karabas-go/firmware/firmware.uf2` |
| `karabas_mini` | 2 | Karabas Mini | `.kg2` | `karabas-mini/firmware/firmware.uf2` |
| `karabas_minig` | 3 | Karabas Mini G | `.kg3` | `karabas-mini/firmware/firmware_g.uf2` |

The firmware is checked on Mini G hardware; Go and Mini have not been checked on hardware since the move to FreeRTOS.

- **Toolchain.** The earlephilhower arm-none-eabi gcc 14 (pico-quick-toolchain 4.1.0, the one PlatformIO installed as `toolchain-rp2040-earlephilhower`): its newlib has dynamic reent and retargetable locks, which `src/platform/newlib.c` needs (it stops the build with `#error` on another newlib). Put its `bin` on `PATH` or pass `-DPICO_TOOLCHAIN_PATH=...`.
- **Versions are pinned** in `CMakeLists.txt`: the pico-sdk 2.2.0 (TinyUSB 0.18.0) and FreeRTOS-Kernel V11.2.0. They come from `PICO_SDK_PATH` / `FREERTOS_KERNEL_PATH` (the environment or `-D`, they must be checked out at these tags), or CMake fetches them. Only bump them deliberately and re-check on hardware.
- To build all boards: `cmake -S . -B build -G Ninja && ninja -C build`; one board: `ninja -C build karabas_minig`. The uf2 files are `build/karabas_<board>.uf2`. A change must keep all three compiling without warnings (`-Wall`). CI (`.github/workflows/build.yml`) builds all three and runs the tests.
- `main()` (`src/main.c`) sets 120 MHz, claims pio1 for the USB host, starts the `USBD` task and creates `APP` and `USB`. `karabas_setup`/`karabas_loop` run in the `APP` task pinned to core 0, and the USB host runs in the `USB` task pinned to core 1 at high priority. The FreeRTOS settings are `src/FreeRTOSConfig.h`, TinyUSB's are `src/tusb_config.h`.
- **Tasks and shared resources:**
  - `APP` (core 0) runs the firmware loop.
  - `INPUT` (core 0, priority above `APP`) forwards usb, ps2 and joystick events to the FPGA as soon as they arrive. It hands anything that needs the UI to `APP` and waits for `APP` on a hotkey.
  - `USB` (core 1) runs the USB host.
  - `USBD` (core 0, above `APP`) runs the USB device stack (`tud_task()`, CDC, MSC callbacks): `tud_task()` blocks on TinyUSB's event queue, the USB irq only queues the events (`src/usb/usb_device`). In MSC mode the SD card is read and written from this task.
  - SPI0 (the FPGA link and FT812) is shared. Every transfer holds `spi_bus_lock`. Take `spi_bus_lock()` / `spi_bus_unlock()` around multi-frame sequences that must not interleave, such as core load, ROM and file transfers (C has no guards: every early return unlocks first). It nests: the owner task and a depth counter (`fpga/link.c`), the FreeRTOS mutex and the hang marks only at the outermost level. A frame is ~3 us on the wire and a mutex take ~8 us, so a loop of many frames takes the lock once around them (`osd_update()` through the `osd_bus_lock` hook of `lib/osd`): per frame locks made a text OSD redraw ~60 us a frame.
  - Incoming FPGA commands are always handled in `APP`. Frames received by another task are queued and handled by `link_dispatch_pending()`.
  - `MATRIX` (core 0, above `APP`, exact 20 ms period) and `OLED` (core 0, `APP` priority, time-sliced with it) run the display frames. Each task is created only if its device was found. Matrix animation timing is counted in frames, not timers, so it stays even. While a core loads, the matrix is in `MATRIX_MODE_LOADING` and only the loader draws its progress bar. A full OLED frame is about 12 ms of busy-polled I2C. The bus runs at 400 kHz, set in `karabas_setup` (`i2c_dev_begin`).
  - I2C is shared by `MATRIX`, `OLED` and `APP` (RTC/EEPROM through hooks in `lib/rtc` (`rtc_*`), matrix commands from the FPGA, the Go extender). Hold `i2c_bus_lock()` / `i2c_bus_unlock()` around every I2C access. The device drivers are C modules in `lib/i2c` on the pico-sdk `hardware_i2c` (`i2c_dev`: the bus, transfers with a timeout, a probe by a one byte read; `ds3231`, `eeprom24` (24C08), `pca9536` (the Go extender), `ht16k33` (the matrix), `ssd1306` (the OLED)); they take no lock themselves. **Lock order:** taking the I2C lock while holding the SPI lock is fine, but never call `spi_send()` while holding the I2C lock. FPGA command handlers run after the SPI lock is released.
  - SD and the OSD state are used only from `APP` (in MSC mode, SD from `USBD`). Keep it that way, or add a lock first.
  - **USB device calls from a task** (`tud_cdc_*`) need no lock of their own: TinyUSB runs on `OPT_OS_FREERTOS`, its fifos are guarded by FreeRTOS mutexes, and the pico-sdk locks block a task (the FreeRTOS interop of the pico-sdk), not the core.
  - **Hang diagnostics** (`src/diag/hang_diag`, debug=1): `hang_mark()` / `hang_step()` marks of `APP`, the SPI / I2C lock owners and heartbeats in the watchdog scratch registers 1..3; the watchdog resets a board whose `APP` stands for 8 s or whose core0 stops, and the next boot logs `Last boot hung: ...`. Every `panic()` (`-Wl,--wrap=panic`: TinyUSB's driver, FreeRTOS asserts) is kept too and logged as `Last boot panicked: "<message>"`, and every `halt()` (the alternating LEDs, also with debug=0) as `Last boot halted: "<message>"`.
  - **USB diagnostics** (`src/diag/usb_diag`, debug=1): a root port disconnect of PIO-USB (`USB root: disconnect` with the line state and who drives D+ / D-), and on the `DIAG` line the SOF rate, the longest frame gap and handler, the root port, its counters. Keep `CFG_TUSB_DEBUG` 0: its log goes to the pico-sdk stdio, which is off (the UART0 pins GPIO 0 / 1 are the SD card of the Mini boards). `third_party/pico_pio_usb` is upstream 0.7.3 with our diagnostics (`pio_usb_diag`, `pio_usb_host_root_state()`, `pio_usb_host_programs_loaded()`, all marked `karabas`): keep our changes small and marked, so a newer upstream can be taken the same way. A dead USB host with the line in SE0 for good and both pins inputs means the Mini G hub (FE1.1s) let go of D+. Both pins `pio1 out 0` would be our own tx stuck in its EOP: a SOF that finds SE0 driven by us lets the lines go and counts it as `own` (0 is normal).
  - **Debug output.** Only `APP` writes to the USB CDC: the log and the serial bridge (`tud_cdc_write`). Use the `d_print*` macros (`src/diag/debug_out`), which buffer output from other tasks, core 1 and IRQs, and all output until a terminal opens the port (8 KB), so the boot log survives a reboot. Check the port with `tud_cdc_connected()`. The pico-sdk stdio is not linked.
  - **Hardware spinlocks.** Only 8 can be claimed with `spin_lock_claim_unused()` (24..31), and the SDK takes some. PIO-USB claims one more when the USB host starts (`alarm_pool_create` in `pio_usb_host_init`), and if none is left the USB task panics: core1 stays at 0 loops in `DIAG` and no USB device ever mounts. Do not claim a new spinlock for a new lock: use `usb_host_lock()` (`src/input/usb_joy.h`) for USB host data or a FreeRTOS primitive. The boot log shows `USB host: N hardware spinlocks free`.
  - **The flash cache.** Both cores run from flash through one 16 KB XIP cache, and `APP` and `USB` never block. A busy loop running through flash code takes the other core's code out of the cache (the USB loop from flash made `APP` 2-3 times slower). `usb_task` and everything its idle turn calls are in RAM (`__not_in_flash_func`); `tuh_task()` runs only when `tuh_task_event_ready()`. Keep new code in the USB loop in RAM, or behind a check that skips it when idle. The `DIAG` line shows the cache hit rate (`xip hit`, ~95% is normal) and `clk_sys`.
  - **USB host limits.** Pico-PIO-USB has 32 endpoints in all (`PIO_USB_EP_POOL_CNT`, the 32-bit `ep_complete` masks), shared by every device and hub: one for control plus one per interrupt / bulk endpoint. A device whose endpoint does not fit loses that interface. Raising the device limits further gains nothing past this pool.
  - **Lost wakeups.** pico-sdk locks (mutex, queue, semaphore) released from an IRQ wake their waiters through the FreeRTOS timer task (`xEventGroupSetBitsFromISR`). `APP` and `USB` never block, so that task runs at the highest priority (`src/FreeRTOSConfig.h`, asserted in `main.c`). Do not lower it. Prefer FreeRTOS primitives or plain spinlocks between tasks.
- `DIAG_STATS=1` prints a `DIAG` line every 10 s when `debug=1`. It shows the loop rate and worst loop gap per core, the free heap and the free stack of the tasks.
- To run the unit tests: `cmake -S test -B build-test -G Ninja && ninja -C build-test && ctest --test-dir build-test`; a single suite: `ctest --test-dir build-test -R test_kg_format`, or run `build-test/test_kg_format`. Every `test/test_<name>/` is one executable on Unity (fetched by CMake). The tests cover only `lib/common`, built for the host.
- To upload: put the board into BOOTSEL (`AT+KARABAS=boot`, a 1200 baud open of the CDC port, the `bootsel` button action, or BOOT at power on) and copy `build/karabas_<board>.uf2` to the `RPI-RP2` drive.
- `BUILD_VER` (shown in About) is the `-DBUILD_VER=...` of the CMake configure. Releases are made by CI only: a master build with firmware changes gets a date stamp version, becomes a GitHub release and is committed into the sibling repos `karabas-go` / `karabas-mini` (`firmware/`), see `.github/workflows/build.yml` (the `SIBLING_REPOS_TOKEN` secret).
- To debug, set `debug=1` in `karabas.ini`, which enables the `d_print*` macros. `-DCMAKE_C_FLAGS=-DWAIT_SERIAL=1` makes the boot wait for a terminal on the CDC port.

## Architecture

**Dual-core split**:
- Core 0: the `APP` task runs everything else. `karabas_loop()` in `src/main.c` calls the module ticks in order: MSC, RTC, UI timers, buttons, UI events from `INPUT`, key repeat, OSD redraw, FPGA command dispatch, serial bridge, ESP, link poll. The order matters, so keep it when adding a tick. `INPUT`, `MATRIX` and `OLED` also run on core 0 (see the task list above).
- Core 1: the `USB` task only runs the TinyUSB host stack on PIO-USB (`tuh_task`). HID callbacks in `hid_app.c` push events with `spi_queue()`, which wakes `INPUT`. The keyboard report crosses cores only through `hid_kbd_report_sync()`, the mouse moves for the graphic menus through `hid_mouse_take()` (sums under `usb_host_lock()`).

**Layout and names.** File and directory names are lower case `snake_case`, except names fixed by others (`FreeRTOSConfig.h`, upstream files). `src/` has only `main`, `config.h`, `types.h`, the FreeRTOS / TinyUSB configs at its top; every module is in a subdirectory. `lib/` holds our libraries (`common`, `ft812`, `i2c`, `ms_time`, `osd`, `rtc`, `sd`, `spi0`), `third_party/` upstream code (`fatfs`, `pico_pio_usb`, `tusb_xinput`: upstream file names, our changes marked `karabas`). Includes of `src/` headers are relative to `src/` (`"apps/app_core.h"`); a new directory under `lib/` or `third_party/` goes into `KG_LIB_DIRS` of `CMakeLists.txt`.

**Modules** (`src/`):
- `apps/`: the OSD screens `app_*` (see OSD apps below).
- `fpga/`: `link` (SPI protocol), `bitstream` (FPGA configuration), `core_loader` (core file header, OSD items, ROMs, `do_configure`).
- `input/`: buttons, joysticks, the core 1 event queue and global hotkeys, the PS/2 keyboard (`ps2kbd`, `usb_hid_keys.h`).
  - The on-board buttons follow the actions of the core (`core.btn`, header `FILE_POS_BUTTONS`, make_core `buttons`): `core` sends `CMD_BTN` (the default, also for older core files with `FF`), or a global action (`osd`, `menu`, `reload`, `bootsel`, `msc`, `msc2`) on the press or on a hold, `input_tick_buttons()`. Nothing is hardcoded for a button: the boot core gets its actions from its `core.json` too. `usb_joy` holds the two USB joystick ports, shared by HID (`drivers/*.ini`) and XInput pads: a pad keeps the port it took when plugged in.
- `ui/`: OSD state and the app table, the drawing helpers (`ui_draw`), the file browser of the text OSD (`file_browser`, `fb_*`: the sorted list of a dir with its own state, the eject / physical drive / `.` / `..` entries, the page drawing and the name cache; used by the file loader and the F / FL items of the core menu, which only fill it), the sorts (`sorts.h`), the OSD font and the logos (`osd_font.h`, `bitmaps.h`).
- `storage/`: SD card, `karabas.ini` settings, USB MSC and the open core file (`file`).
  - MSC mode starts only on a reboot asked through watchdog scratch 0 (`msc_reboot_to_msc()`: `AT+KARABAS=msc`, the `msc` button action). The boot core is loaded first and shows the msc screen (`app_msc`, text or FT812), then `msc_start()` hands the card to the PC; ejecting it reboots, when the host lets the device go (`tud_umount_cb` / `tud_suspend_cb`: Windows "Safely Remove" ends with the port disabled) or 5 s after the eject (Linux, Explorer's Eject). Rebooting at once made the Windows 10 removal hang with "not removable" (msc2); no reboot on a suspend without an eject (a host may autosuspend an idle drive). With debug=1 the start/stop commands and the USB events are logged. The eject callback (`USBD`, like the read / write ones) ends the open multi-sector transfer with `sd_card_sync()` and refuses later reads: on the dedicated bus of SD1 a multi-sector transfer stays open between calls, and the card stayed in it over the reboot and the bitstream read of the boot core stopped half way (`CONF_DONE timeout`, a second reboot).
  - The second SD card (the slot of the FPGA, `storage/sd2`): the boot core passes it through to the MCU link (`kg_mcu` `ENABLE_SD2`: SCK / MOSI / MISO of SPI0, chip select `PIN_MCU_SD2_CS`), so the MCU reaches it only while the boot core runs. `sd_card` (`lib/sd`) on a shared bus: SPI0 through `spi0_bus`, every transfer under the SPI bus lock (a failed transfer is logged, the card is set up again and the transfer tried once more), 12 MHz (24 MHz fails through the FPGA; SPI0 divides 48 MHz, so a 16 MHz request is 12 too). It is used for MSC mode with the second card (`msc2`: the button action, `AT+KARABAS=msc2`, its own scratch 0 magic; the USB name "SD Card 2" is set in `msc_init()` from the request, the PC asks it before `msc_start()`; no card: the msc screen says so and the board reboots after 5 s) and `AT+KARABAS=sd2test` (reads at 4..24 MHz with link frames between the blocks; it never writes). The boot menu has `msc2` on a 2 s hold of BTN2.
  - The SD card (SD1) is read through FatFs R0.15 (`third_party/fatfs`, own `ffconf.h`): FAT16, FAT32 or exFAT, long names in UTF-8, no current dir (full paths: `/dir/name`, or `name` in the root), file times from the RTC (`get_fattime`). Its disk I/O and the helpers (`sd_open`, `sd_read`, `sd_write`, `sd_exists`, `sd_mkdirs`, `sd_read_all`) are in `storage/storage`. The card driver is `lib/sd`: `sd_card` (the SPI mode protocol of SdFat's SdSpiCard) on `sd_pio` (the PIO SPI, 16 MHz, a dedicated bus). A `FIL` has its own 512-byte buffer: keep them out of the task stacks (`static`). exFAT has no 8.3 names, so the file lists and the saved image names use the long names (`FILINFO.fname`). Files in a list are found by id: `sd_file_id()` / `sd_find_id()` (the karabas additions to FatFs: `FILINFO.dir_ofs` and `f_readdir_at()`; a third one in `f_lseek` takes the cluster of a contiguous exFAT file straight away: FatFs walked it cluster by cluster, over a second at the end of the 14 GB HDF of nanomig, and AmigaDOS read wrong blocks). The id is SdFat's `dirIndex` of older firmware (the file loader saves it into the core file): the short name entry index on FAT, the file entry index + 1 on exFAT (the first file of a subdir has index 0 and 0 means no file). `f_lseek` past the end of a file open for writing grows it: check the size first (`img_mount`).
  - The core menu items (`core.osd`): `core_osd_selectable()` (options or a file item: the cursor stops on it, `kg_list_step_active()` skips the text rows) and `core_osd_change(pos, d)` (the next / previous option, sent to the core, a switch saved later): the menu keys and the core's hotkeys both go through it.
  - `FL` OSD items (ioctl file loader): `core_ioctl_send()` in `fpga/core_loader` sends the file when it is chosen, and at core start if the item has `autoload` and its file exists (the NanoMig Kickstart).
  - In the OSD, the browser of an `F` slot without an image opens in the dir of the image chosen last for a slot with the same extensions, on the file after it (disk 2 after disk 1). Esc goes back to the slot's own dir.
  - `img_mount` is the file mounter (`F` OSD items). The image of a slot stays open while the core runs. The link handlers only take the sector requests of the core (`CMD_IMG_LBA` / `CMD_IMG_SEC`), and `img_tick()` serves them from the main loop. A read sends the sector as a burst or classic frames; a write pulls the 512 bytes of the core with NOPs. Sequences are in `docs/protocol.md` section 6.
  - `bk_save` is the backup RAM (`.sav`) of cores with caps bit 3 (`CAPS_BK`, `link_core_caps()`): the core asks with `CMD_BK_MOUNT` after a game is loaded, `bk_tick()` creates `<save_dir or <fileloader dir>/saves>/<game>.sav` and mounts it in the slot the core named through `img_mount`. `bk_flush()` (`CMD_IMG_FLUSH`, serving the write requests until the answer) runs before the file loader sends another game, in `do_configure()` before another core, before the reboot hotkey, `AT+KARABAS=boot` and the reboot into USB MSC. The FPGA side is `kg_bk_ram` of `karabas-go-modules` (the NES core), `save_dir` is a `make_core` field. `docs/protocol.md` section 6, "Backup RAM".
  - Physical floppy drives (Karabas Go, `board_has_floppy()`): the browser of an `F` item with `CORE_OSD_FLAG_PHYS` (the flags byte after the item type, `"physical": 1` in `core.json`) has `[ Physical DF0 ]` / `[ Physical DF1 ]` after `[ Eject ]`. The slot then keeps the file name `:phys0` / `:phys1` (`kg_phys_drive()`), and `img_mount` sends `CMD_IMG_PHYS` after the size 0 frames instead of opening a file. A drive is in one slot only.
- `periph/`: the LED matrix, OLED and USB serial bridge.
  - `esp_at` is the non-blocking AT client of the ESP8266 behind the FPGA (`periph/esp_serial`, a C module with two 4 KB rings, `CMD_ESP_UART`, bridged by the BOOT core only): `esp_at_start()` then `esp_at_poll()` from a tick. The bytes move only in the main loop (link dispatch, `esp_serial_handle()`), so never wait for a reply in a loop.
  - The bridge forwards the host's bytes to the core UART (`CMD_UART`), except `AT+KARABAS=<cmd>` lines, which the firmware answers itself: `list` (the cores on the SD card with their builds), `boot` (reboot into BOOTSEL), `msc` / `msc2` (reboot into USB mass storage with the first / second SD card, requested through watchdog scratch 0), `sd2test` (BOOT core only: a read test of the second SD card), `esp` (BOOT core only: the bridge goes to the ESP8266 uart, `esp_tick()`; it steps aside while `esp_at_busy()`) and `uart` (back to the core). Bytes that may start such a line are held back until they can't, or for 500 ms.
- `usb/`: the USB device (`usb_device`, `usb_descriptors`), the host class drivers (`host_drivers`, `printer_host`) and the HID / XInput host callbacks (`hid_app`, `hid_driver`: the pad ini drivers, `xinput_app`).
- `board/`: per-board code (see below).
- The firmware is C11 (`.c`); the headers have `extern "C"` guards. Debug output goes through `debug_print` / `debug_printf` (`diag/debug_out`, behind the `d_print*` macros).
- `main.h` is an umbrella header that includes every module header. Each module owns its state, and state is `static` unless other modules need it.

**MCU↔FPGA SPI protocol**: (full description: `docs/protocol.md` / `docs/protocol.ru.md`; keep them in sync with `config.h` when commands change)
- Every transfer is a 3-byte frame `cmd, addr, data` (`spi_send`). The FPGA replies with a 3-byte frame in the same transaction. Any non-zero reply cmd is dispatched to the handler registered with `link_on(cmd, fn)`, so the FPGA can only send data when the MCU sends something. Handlers are registered in `karabas_setup()` and `matrix_register_handlers()`. Incoming commands are ignored while the FPGA is being configured (`link_set_rx_enabled`).
- All `CMD_*` opcodes are defined in `src/config.h`, along with short comments on the multi-byte sequences for the file mounter (`CMD_IMG_*`, full description in `docs/protocol.md`) and the file loader (`CMD_IOCTL_*`).
- A new command needs matching support in the FPGA cores, which live in a separate repo.
- The SPI clock defaults to 16 MHz. A core can override it with its `spi_freq` header field, which `read_core()` passes to `link_set_freq()`.
- **Burst transfers** (`docs/burst_protocol.md`). A second chip select (`PIN_BURST_CS` = `PIN_MCU_SPI_IO0`), optional `PIN_BURST_READY` = `PIN_MCU_SPI_IO1`, a 5-byte header (type + 32-bit address) and up to 512 data bytes.
  - They are used only if the core answered the `CMD_CAPS` query that `do_configure()` sends. Otherwise everything stays on classic frames, so old cores are unaffected.
  - ROMs, the file loader and ioctl data try `link_burst_write()` first and send the rest with classic frames.
  - **MCU_IO4 (GPIO18) must stay an input:** on modded Mini boards it is the FT812 clock from the FPGA.
  - `PIN_BURST_CS` is pulled up while the MCU does not drive it, and the cores pull it up too. A floating chip select lets a core's burst receiver take classic traffic for a burst.
  - Bursts are always used when the core supports them (there is no switch). With `debug=1` the log shows the ROM, file loader and ioctl transfer times with the link mode. The file loader also logs the CRC-32 of the sent file, which can be compared with the file on a PC.

**Core files (`.kg1/.kg2/.kg3`)**:
- Each file has a fixed binary header followed by the FPGA bitstream. Field offsets are the `FILE_POS_*` constants in `config.h`. The bitstream starts at 1024. EEPROM and switches data live at 256 and 512.
- After the bitstream comes a ROM section made of blocks. Each block has a big-endian `len` (bit 31 means external), then `addr`, then `len` bytes of payload: ROM data, or the filename of an external ROM. The writer is `make_core` in the sibling `karabas-go-tools` repo.
- Some fields are written back into the core file itself, such as the file loader dir and filename and the saved OSD switches.
- `read_core()` parses the header into the global `core` (`core_item_t` in `types.h`), including the OSD item definitions.
- `fpga_send()` (`fpga/bitstream.c`) streams the bitstream through the `PIN_CONF_*` pins with the `fpga_serial.pio` program fed by DMA. CCLK is `FPGA_CCLK_HZ`, 20 MHz by default. If no PIO state machine or DMA channel is free, it falls back to bit-banging.
- **PIO and DMA budget.** PIO-USB on core 1 hard-claims DMA channel 0 at init: firmware code takes DMA channels from the top and claims PIO resources only after `usb_host_ready` is set. The usb host takes all of pio1 (`USB_HOST_PIO` in `main.c`): tx, rx and eop share the block (5 + 10 + 17 = all 32 instruction words, sm0..2), upstream's main path (the receiver is armed in hardware at our EOP). pio0 is for the firmware: the PIO SPI of the SD card (`sd_pio`), `fpga_serial`. `main()` claims the pio1 state machines first thing, so nothing else lands there. Nothing else may load programs into pio1. `pio_usb_host_programs_loaded()` logs an error when the PIO-USB programs do not fit.
- `fpga_serial.pio.h` is generated by pioasm and committed, so edit the `.pio` file and regenerate it (the command is in the `.pio` file).
- Core types: BOOT (the core browser), OSD (a normal core with an overlay menu), FILELOADER, and HIDDEN.

**OSD apps**:
- `osd_state` (`osd_state_e` in `types.h`) selects which `app_*.c` module owns the overlay and the keyboard: `app_core` (the per-core menu and file mounter), `app_core_browser`, `app_file_loader`, `app_setup`, `app_rtc` (Setup > Setup RTC: the date and time typed into masked fields, `masked_input`; BOOT core only: the time zone `karabas.ini [setup] tz` (UTC offset, 15 min steps, no DST) and NTP sync, which sets the RTC through `periph/ntp_sync`: `AT+CIPSNTPCFG` with timezone 0 and `AT+CIPSNTPTIME?`; old AT firmware without these commands just gets an error. The FT Clock page has the same; it saves `tz` itself and `app_ft_setup_tz_saved()` updates the setup's copy), `app_wifi` (Setup > Setup Wi-Fi, BOOT core only: status, scan, password, join; turns on the ESP CTS flow control with `AT+UART_DEF=115200,8,1,0,2`; Update module: the AT firmware over the air from Espressif's server, `AT+CIUPDATE`, Reset module: `AT+RESTORE`, both through `periph/esp_update` with an estimated progress bar), `app_ft_setup` (the graphic setup of the FT812 browser, `S`: sections on the left, live preview, a new video mode is tried and kept only when confirmed; the Clock, Wi-Fi and Gamepad tabs are pages of their own modules `app_ft_clock`, `app_ft_wifi`, `app_ft_pad` behind `ui/ft_page.h`. The clock editing is shared: `apps/clock_edit` (`ce_*`: the fields, the time zone, writing the RTC, NTP sync, the message) is the model of `app_rtc` and `app_ft_clock`, which only lay it out. So is the pad learning: `apps/pad_learn` (`pl_*`: the steps from finding the pad to saving its driver ini) runs under `app_pad_mapper` and `app_ft_pad`, which keep their port list (and the FT test). So is the Wi-Fi setup: `apps/wifi_setup` (`ws_*`: the AT steps of the status, the scan, the join, Forget, Update / Reset module, the screens and the keys) under `app_wifi` and `app_ft_wifi`, which draw it (and map the mouse)), `app_settings` (Setup > Settings, BOOT core only: the `karabas.ini` keys of `[setup]`, `[matrix]`, `[autoload]` and `enabled` / `video_mode` of `[ft812]`; `save_setup()` writes only the changed keys through `karabas.new` with `kg_ini_update`), `app_about` and `app_pad_mapper` (Setup > Map USB gamepad: opens on the two joystick ports with what maps each pad, `usb_pads_get()` in `hid_app.c`; Forget is `hid_driver_forget()`; Map learns a pad from its raw reports through `hid_capture_*` (`apps/pad_learn`) and saves a driver ini with `hid_driver_save()`).
- `osd_handle()` redraws the overlay whenever the state changes, and `ui_on_keyboard()` routes keys. Both go through the `apps[]` table in `ui/osd_ui.c`, which is indexed by `osd_state_e`. A new screen needs an enum value and a table entry in the same order. An entry can have an optional `tick`, called from `ui_tick()` while its app owns the OSD.
- **Keys of the OSD apps.** A screen reads its key with `ui_nav_key()` (`ui/osd_ui`): the keyboard key, else the pad's, so the pad means the same on every screen: directions, A / B Enter, C / Mode Esc (Left / Right change a core menu option). Do not test `joyL` / `joyR` bits in a screen. A list moves with `ui_list_key()` (`kg_list` in `lib/common`: Up / Down by one around the ends, Left / Right a page).
- **Drawing the text screens** (`ui/ui_draw`): `ui_screen(title)` (cleared, the header, the clock, the title at row 5 with a line under it), `ui_hint(line1, line2)` (the line at row 23 and the two hint rows), `ui_row(x, y, text, selected)` (a row to the right edge, padded), `ui_hotkey(key, rest)` (a flashing cyan key letter). Use them and the `UI_ROW_*` rows instead of placing and padding by hand. Page counts are `kg_list_pages()` / `kg_list_page()` (no float).
- Buttons of the OSD apps are drawn with `ui_button()` (`ui/osd_ui`): no brackets, the label centered, yellow when focused, grey otherwise. Buttons on one screen have the same width. Text cursors are cyan.
- The settings of both Settings screens (names, hints, values, changes, the color themes) are in `ui/settings_items`; each screen only draws them.
- The mouse of the graphic menus is `ui/ft_mouse`: a screen ends its frame with `ft_frame_end()` (the frame is kept in GRAM, a pointer move only appends it with `CMD_APPEND`), adds its clickable areas with `ft_hit_add()` while drawing, and polls `ft_mouse_poll()` from its app tick. Keys, joysticks and the mouse are not forwarded to the core while the OSD is open.
- The core browser has two renderers: a text one through the FPGA OSD (`lib/osd`, `osd_*`) and a graphical one through the FT812 (`lib/ft812`, `ft_*`: only what the firmware uses), used when it's present and enabled.

**Per-board code**: pin maps are in `config.h`. Board behaviour lives behind the `src/board/board.h` API, implemented by `board_go.c` (I2C extender, Sega joysticks) and `board_mini.c` (Mini and Mini G, including the Mini G ESP, MIDI and FT reset lines). Outside `config.h`, `bitmaps.h` (logo selection) and `src/board/`, code must not use `#if HW_ID`. Add a `board_*` function instead.

**`lib/common`**: hardware-independent logic in C11 with no pico-sdk includes, unit-tested on the host (`test/`, C11 on Unity). It contains `kg_format` (core file and ROM block parsing), `hid_joy_map` (`drivers/*.ini` mapping), `hid_auto_map` (the default map of a HID pad built from its report descriptor, used when there is no driver ini; see `docs/usb_gamepads.md`), `hid_learn` (learning a driver ini from raw reports, for the OSD mapper), `kg_matrix` (the LED matrix block of a core file, text placeholders), `matrix_fx` (the matrix effects on a 16x8 buffer), `matrix_style` (the karabas.ini look of the clock and the meters), `matrix_meter` (the audio meters), `crc32`, `at_cmd` (the `AT+KARABAS=` line parser of the serial bridge) `masked_input` (the masked date / time fields of the OSD), `esp_at_parse` (ESP8266 AT reply lines, quoting), `time_zone` (the `tz` UTC offset, date + minutes, a valid date, the day of the week, the build date), `rtc_regs` (the BCD time registers of the DS3231), `font5x7` (the 5x7 font of the matrix scroll, glcdfont of Adafruit GFX), `hid_ascii` (HID usage to ASCII for OSD text fields), `ini_update` (writes new values into an ini file line by line, keeping the rest), `file_name` (extension match and short names of the OSD file lists, the string / path helpers `kg_trim`, `kg_path_*`) and `kg_ring` (a byte ring buffer, the ESP uart rings of `periph/esp_serial`) and `ini_read` (karabas.ini and the pad drivers). New pure logic that is worth testing goes here.

**`tools/hidmapper`**: the browser gamepad mapper (Vue + WebHID), published to GitHub Pages by `.github/workflows/hidmapper.yml` (https://andykarpov.github.io/karabas-go-firmware/hidmapper/). Its `JoyMap.ts`, `HidLearn.ts` and `AutoMap.ts` port `hid_joy_map`, `hid_learn` and `hid_auto_map`, with the same test cases. A change to one side needs the other. Tests: `cd tools/hidmapper && npm ci && npx vitest run`.

**Runtime config**: on the SD card, `karabas.ini` is read by `load_setup()` (`storage/settings`). The file is optional: the defaults live only in `load_setup()` (there is no example file), and the first save from the menus creates it. The keys and their defaults are listed in README.md / README.ru.md (`[matrix]` in `docs/matrix.md`): update them with a new key or default. It is read whole and parsed with `kg_ini_read` (`lib/common`). Every line, comments included, must fit in 78 chars and the line end (the limit of the reader before it, kept so a file behaves the same). A longer line makes `kg_ini_valid()` reject the whole file, and the firmware silently falls back to the defaults (it logs `karabas.ini is invalid`). USB joystick mappings are `*.ini` files in `/drivers/` on the SD card, described in `docs/usb_gamepads.md` (Driver ini).

**Optional peripherals** are detected at boot and tracked by flags (`has_ft`, `has_matrix`, `has_oled`, `has_extender`, ...). Code should check the relevant flag before touching the device. The dot-matrix add-on and its ZX-side register interface are documented in `docs/matrix.md`. What the matrix shows is set per core by `core.matrix` (`FILE_POS_MATRIX` 768, make_core `matrix`, parsed by `kg_matrix` in `lib/common`): `core` (the default: the core draws or shows its meters, the boot core scrolls `KARABAS GO`), `scroll`, `effect` (`matrix_fx`: clock, fire, life, scanner, rain, plasma, stars, pong, drive: the image slots of `img_mount` through `matrix_drive_mount()` / `matrix_drive_access()`), `image` (up to 4 frames), `blank`, with `repeat` / `then`. `CMD_MATRIX_*` from the core are ignored outside the `core` mode. `karabas.ini [matrix]` `enabled` / `brightness` (0 = the core's) and the look of the clock and the audio meters (`clock_*`, `meter_*`: `lib/common` `matrix_style` / `matrix_meter`; Settings > Matrix effects and FT System > Matrix effects, where the matrix previews the plugin being edited, `matrix_preview()`) apply to all cores (Settings shows the edited values at once through `matrix_setup()`, `settings_end()` puts back hw_setup when it is left unsaved). The pixel colors of `CMD_MATRIX_PIXEL` are the HT16K33 ones (2 yellow, 3 green): the cores use them as they are. Before a reboot into BOOTSEL and in MSC mode the matrix shows a static icon (`matrix_icon()`): the bootrom leaves it as it was.
